## 4. Proposed 90-day pre-chain program — **not ratified token allocation**
**Campaign name:** Genesis Season Zero — Agent Economy. **Length:** 90 days in three 30-day Acts, with 7-day weekly epochs (the final epoch is a partial period). **No mandatory wallet.**
- Act I (Days 1–30): play and qualify; collect verified daily/weekly events, invite quality, establish true D1/D7 baseline.
- Act II (Days 31–60): creators, leaderboards, first real agent tasks, public showcases, crew, ambassadors, partner missions.
- Act III (Days 61–90): product-use depth, audited scoring, allocations simulator, snapshot preparation, eligibility review and documented appeals.
- Token/contract release remains a separately verifiable workstream; 90 days is a campaign duration **not a promised TGE deadline**.

### Candidate pool linked to EXISTING hypothetical 100M model
- Existing public modelling: **100,000,000 hypothetical units** total, 30% community = **30,000,000 model units**; not minted.
- **Propose** reserving **3,000,000 hypothetical units (3% total; 10% of community bucket)** as Season Zero *candidate* pool. This is a research design, **not an existing budget, enforceable promise or commitment**. Publish as a candidate until token/economic rights and season rules are formally set.
- Five bucket allocation candidate:
  - 40% (1,200,000) verified participation + genuine returning days;
  - 25% (750,000) agent creation and verified agent-task output;
  - 15% (450,000) qualified first-level referrals;
  - 10% (300,000) crew outcomes and team collaboration;
  - 10% (300,000) accepted quality feedback, bug fixes and community steward work.
- Unused bucket amounts carry forward to a later community pool (no hidden reallocation). A user may earn from multiple buckets. One verified human's aggregate candidate share is capped initially at 0.25% of Season Pool (7,500 model units), with deterministic redistribution policy published before commitment.

**Formula (only after a pool has actually been authorized):**
`allocation_i = sum_over_buckets(pool_b × eligible_adjusted_score_i,b / sum_eligible_adjusted_scores_b)`.
No score or XP is directly exchangeable at a guaranteed rate now. The personalized app must show *actual XP, current eligible activity, tentative score and possible scenario*, never a claimable token or dollar amount before real issuance.

**Per-user illustrative arithmetic (NOT personal quotes):**
- If 1,000 users qualified equally and there were no caps: 3,000 model units/user.
- If 5,000 users qualified equally: 600 model units/user.
- If 10,000 users qualified equally: 300 model units/user.
- Actual outcomes will differ by category scores, duplicate accounts, qualification, individual caps and carry-forward rules. Do not use these figures as fixed invite incentives.

### Proposed season scoring vs existing XP
Existing internal XP is unchanged: 5 for daily, 8 for correct daily game, 20 for first real Agent DNA, 10 for accepted feedback weekly, 25 for activated inviter, plus existing streak rules.
Use separately computed 0–100 normalized component scores with weights:
- Agent usage/result quality **30%**,
- Return days and meaningful daily activity **20%**,
- Accepted creator/build tasks **20%**,
- Qualifying referrals **15%**,
- Verified quests & community service **15%**.
Each component is capped and decays above its threshold; one-level referrals only. No purchase/paid boost produces more season eligibility. Publish the weights, eligibility and anti-fraud process before treating any season score as allocation-bearing.

**Referral qualification (proposed stricter gate):** referred account registered, returned on a second separate UTC day, completed three distinct qualifying actions (including at least one Agent DNA save OR real Agent task proof), and passed proportionate anti-Sybil checks. Referral reward stays pending until all gates pass. The current internal +25 XP after first agent remains as-is until new program rules and tests deliberately version it.

## 6. Real analytics/OS event design, privacy, attribution
Source event schema: `event_id, occurred_at_utc, event_type, user_id, workspace_id, session_id, anon_id?, campaign_id?, referrer_id?, utm_source?, utm_medium?, utm_campaign?, property_map, proof_ref?, idempotency_key, accepted, rejection_reason, rules_version`.
Core events (new instrumentation, do not misrepresent as deployed):
`landing_view, signup_start, signup_complete, genesis_join, first_daily_claim, daily_game_complete, quest_submit, quest_accept, agent_dna_save, agent_task_start, agent_task_success_verified, proof_card_shared, referral_link_opened, referral_signup, referral_qualified, crew_join, crew_goal_met, notification_opt_in, notification_delivered, notification_opened, returned_d1, returned_d7, token_launch_interest`.
- Server-generated event is canonical for rewards. Client telemetry is informational and must not grant tokens or points.
- Attribution: first-touch anonymous campaign (short TTL), sign-up source, invite binding at registration, verified referral from source account; never silently rewrite original referrer.
- Identity is scoped by workspace/account and optionally proof-bound wallet; IP/device alone are **not** proof of a person. Do not use invasive cross-venture profile merging.
- Dashboard views: visitor→signup→first action→day2 return→first agent→verified task→referral qualified; cohort D1/D7/D30; DAU/WAU; qualified/invalid rate; cost per activated user; helpful outcomes per active member.
- OS triggers: `support.case_created` -> triage, `referral.qualified` -> ledger, `d1_missed` -> opted-in reminder, `agent_task_failed` -> incident queue, `weekly_cohort_ready` -> campaign optimizer, `snapshot_proposed` -> operator review. OS may debug and propose changes but no automated wallet transfers or live token sales based on user content.
