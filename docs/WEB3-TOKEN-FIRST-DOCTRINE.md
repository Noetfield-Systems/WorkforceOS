# WorkforceOS Web3 Token-First Doctrine
Edition 1.0 | 18 November 2026

## Venture identity / non-negotiable
WorkforceOS is being developed as a **crypto-native AI-agent economy and community**. The goal is a usable, economically coherent token ecosystem where agents, creators and participants can work, coordinate and grow. The existing customer workspace, Agent DNA, task runtime and billing code are subsystems, not the commercial narrative.

**Do not drift into subscriptions-first SaaS.** No default hero, public help, pricing route, acquisition landing, outbound invitation or executive plan should sell monthly Solo / Builder / Team tiers as the core user proposition. Existing entitlements may continue to run where needed; they do not define venture strategy.

## Product discovery hierarchy
1. Join Genesis without a mandatory wallet; immediately see Claim, play, quest and referral loops.
2. See the public token thesis: **100M hypothetical reference supply**, 30% community, 25% ecosystem, 20% builders, 15% treasury, 10% potential liquidity.
3. Study explicit token price and FDV scenarios: $0.0025/$250k, $0.005/$500k, $0.01/$1M. These are model inputs, never fake live charts or offers.
4. Create a real Agent DNA and obtain a real execution output where the current runtime supports it.
5. Invite real users, measure retained active participants, useful tasks, contribution receipts, activated referrals and token-launch interest.
6. Progress to token design, chain and contract specification, transparent allocation and vesting terms, verifiable launch mechanisms, and actual onchain participation.

## Readiness definitions
- **Live now:** database-backed accounts, Genesis XP/quests, game/streaks, referrals, agent builders, support and buyer-interest case intake.
- **Research / scenario:** supply and allocation model, $0.005 reference input and any token-related valuation arithmetic.
- **Not currently live:** crypto token ticker, minted contract, transferable balance, purchase/claim rights, onchain staking, liquidity/DEX and investment checkout.
- The boundary between these states must be obvious at the point of interaction, with minimal friction and no fabricated market metrics.
- If a real token offering is selected later, specify token rights, issuer, eligibility, distribution, funding route, network, deployer ownership, audited or independently reviewed contracts, transaction verification and actual checkout receipts. Do not disguise an offering as a demo.
- **Founder approval is not an invented blanket gate** for everyday UX/product launches. Clear legal and security requirements for any real sale remain mandatory.

## Benchmarks and learning
- Virtuals: token and agent commerce at the forefront of discovery (https://www.virtuals.io/).
- Olas: token coordinated agent ecosystem and composability (https://stack.olas.network/protocol/tokenomics/).
- Galxe: quest + reward loops with eligibility and visible rules (https://help.galxe.com/en/articles/9645630-create-quest-rewards).
Benchmarks inform the product experience; they do not establish our own real-world token trading, revenue or user metrics.

## Acceptance invariant
After any future design or growth sprint, inspect the public root, /genesis, /genesis/app, /tokenomics, /pricing, /commerce, and /help:
- Genesis + tokenomics outrank subscription sales.
- Member XP remains a truthful recorded balance, not a promised allocation.
- Price scenarios must always be labelled hypothetical until a source-backed market price exists.
- User support and event outbox remain operational.
- No legacy billing subsystem is deleted or detached merely to edit marketing copy.
